# RES-001: Технические варианты и риски захвата экрана на Windows (мультимонитор, HiDPI, горячие клавиши, буфер обмена)

| Поле | Значение |
|---|---|
| Статус | Draft |
| Дата | 2026-10-18 (ред. 2 — учтены ответы на открытые вопросы REQ-001) |
| Связанные | REQ-001, US-001 – US-007 |

## Вопрос исследования

Какие технические средства JVM/Kotlin и Windows API позволяют выполнить REQ-001? Нужно обеспечить:
- захват в физических пикселях при смешанном DPI (REQ-001.7, REQ-001.19, REQ-001.20, REQ-001.N5);
- производительность (REQ-001.N1–N4);
- глобальные горячие клавиши (REQ-001.2, REQ-001.3);
- надёжный буфер обмена (REQ-001.23–REQ-001.26);
- определение и хранение директории по умолчанию (REQ-001.44, REQ-001.45).

Также нужно выявить риски, которые следует снять прототипом (spike) до начала реализации.

## Методика

- Анализ документации JDK (`java.awt.Robot`, `GraphicsEnvironment`, `Toolkit`, `ImageIO`) и Microsoft Learn (High DPI, GDI, DXGI Desktop Duplication, Windows.Graphics.Capture, `RegisterHotKey`, Clipboard, Known Folders).
- Опыт и известные проблемы аналогичных инструментов (ShareX, Greenshot, Flameshot).
- Критерии оценки: точность при смешанном DPI, скорость на 4K, сложность интеграции с JVM, зависимость от нативного кода, риски поддержки.

> Результаты основаны на документации и известных особенностях платформы. Их **нужно подтвердить прототипом** на эталонной
> конфигурации (REQ-001 §4). Код в репозитории пока отсутствует.

## Результаты

### 1. Механизм захвата пикселей

| Вариант | Плюсы | Минусы | Оценка для v1 |
|---|---|---|---|
| **AWT `Robot.createScreenCapture`** | Чистая Java, без нативного кода | Принимает координаты в логических (user-space) единицах. При HiDPI возвращает изображение, уменьшенное до логического размера, — нарушает REQ-001.20 | Не подходит как основной |
| **AWT `Robot.createMultiResolutionScreenCapture`** (JDK 9+) | Чистая Java, есть вариант в физическом разрешении | Координаты по-прежнему логические. При смешанном DPI соответствие логических и физических координат мониторов в JDK неочевидно; возможны разрывы и наложения на стыках. Скорость на 4K требует замера | Резервный вариант, нужен прототип |
| **GDI `BitBlt` / `GetDIBits` через JNA** | Физические координаты виртуального стола (при per-monitor DPI awareness процесса). Простая интеграция через JNA. Один вызов на весь виртуальный стол. Достаточно быстро для 4K (ориентир — десятки мс) | Нативный слой, только Windows. Требуется режим DPI awareness `PER_MONITOR_AWARE_V2` на потоке или процессе. Цвета при HDR искажаются. Exclusive fullscreen и DRM дают чёрный кадр | **Рекомендуется** для v1 |
| **DXGI Desktop Duplication** | Самый быстрый; работает по выходам (мониторам) | Сложная интеграция (COM/D3D11 через JNA или JNI), отдельная обработка каждого монитора и поворотов, ресурсоёмкая инициализация. Избыточно для одиночных снимков | Отложить |
| **Windows.Graphics.Capture** (WinRT, Win10 1803+) | Современный API, корректная работа с HDR | WinRT из JVM — сложно (нужна C++/WinRT-прослойка). Жёлтая рамка захвата в части версий Windows | Отложить |

**Перечисление мониторов:** `EnumDisplayMonitors` + `GetMonitorInfo` (через JNA) дают прямоугольники мониторов в физических
координатах виртуального стола при per-monitor DPI awareness. Масштаб монитора — `GetDpiForMonitor`. Это надёжнее, чем
`GraphicsEnvironment.getScreenDevices()` + `GraphicsConfiguration.getBounds()`: при смешанном DPI JDK возвращает
логические границы, и их сложно однозначно перевести в физические.

**Монитор под курсором:** `GetCursorPos` + `MonitorFromPoint(..., MONITOR_DEFAULTTOPRIMARY)` — это прямо реализует REQ-001.6 и REQ-001.8.

**Исключение собственных окон (REQ-001.21):** `SetWindowDisplayAffinity(hwnd, WDA_EXCLUDEFROMCAPTURE)` (Windows 10 2004+)
или скрытие окон до захвата. Для оверлея «Области» проблема снимается схемой «замороженного кадра»: захват выполняется до показа оверлея.

**Указатель мыши (REQ-001.22, REQ-001.53):** GDI `BitBlt` не включает курсор, поэтому режим «без указателя» (по умолчанию)
выполняется без доработок. Для режима «с указателем» в момент нажатия горячей клавиши нужно:
1. получить форму и позицию указателя: `GetCursorInfo`, затем `CopyIcon` / `GetIconInfo` (горячая точка — `xHotspot`/`yHotspot`);
2. нарисовать указатель на снимке через `DrawIconEx` в memory DC до передачи кадра дальше.

Для «Области» позиция и форма сохраняются вместе с замороженным кадром (оверлей заменит указатель на перекрестие).
Монохромные и анимированные курсоры, а также увеличенный размер указателя в настройках специальных возможностей нужно
проверить в прототипе.

### 2. Оверлей выделения области

- Одно окно на весь виртуальный стол при смешанном DPI ведёт себя непредсказуемо: Windows масштабирует окно под DPI монитора, на котором находится его большая часть.
- **Рекомендуется:** по одному undecorated always-on-top окну на монитор. Каждое окно показывает свой фрагмент замороженного кадра в масштабе 1:1 к физическим пикселям. Выделение ведётся в глобальных физических координатах.
- Отрисовка 1:1 в Swing/Compose при масштабе ≠ 100 % требует учёта текущего scale-фактора (иначе кадр «поплывёт»). Это проверочный пункт для прототипа и вход для ADR о выборе UI-фреймворка.

### 3. Глобальные горячие клавиши

| Вариант | Плюсы | Минусы |
|---|---|---|
| **`RegisterHotKey` через JNA** + поток с циклом сообщений | Штатный механизм Windows. Возвращает ошибку при конфликте (прямо реализует REQ-001.3). Клавиша «поглощается» и не уходит в активное приложение | Только Windows; нужен отдельный поток с `GetMessage` |
| JNativeHook (низкоуровневый хук клавиатуры) | Кроссплатформенность | Не определяет конфликты. Не поглощает нажатие. Глобальный хук клавиатуры может вызывать подозрения у антивирусов. Лишняя зависимость |
| AWT `KeyListener` | — | Работает только при фокусе окна, не подходит |

**Рекомендуется** `RegisterHotKey`. В Windows 11 PrtSc по умолчанию открывает «Ножницы», поэтому выбраны комбинации
с модификаторами `Ctrl+Shift+1/2/3` (REQ-001.52). **Риск:** `RegisterHotKey` перехватывает эти сочетания во всех
приложениях. Например, в Microsoft Excel `Ctrl+Shift+1/2/3` применяют числовой формат, формат времени и даты — пока
приложение запущено, в Excel эти сочетания работать не будут. Митигация — переназначение (REQ-001.4) и упоминание
в документации пользователя.

### 3a. Уведомления

| Вариант | Длительность 3 с (REQ-001.54) | Контент (имя файла + папка, кнопка «Сохранить как…») | Сложность |
|---|---|---|---|
| Toast-уведомление Windows (WinRT `ToastNotification`) | **Нет**: длительность задаёт Windows (параметр специальных возможностей «Показывать уведомления в течение», минимум 5 с). Приложение может только убрать уведомление программно, но toast останется в Центре уведомлений | Да | Высокая: WinRT из JVM, нужен AppUserModelID и ярлык |
| `TrayIcon.displayMessage` (AWT, balloon) | **Нет**: в Windows 10/11 отображается как toast с системной длительностью | Без кнопок | Низкая |
| **Собственное undecorated always-on-top окно** | **Да**: таймер приложения | Да, полный контроль макета | Низкая–средняя |

**Рекомендуется** собственное окно уведомления. Оно должно:
- не забирать фокус (`WS_EX_NOACTIVATE`, `focusableWindowState = false`);
- исключаться из захвата (`WDA_EXCLUDEFROMCAPTURE`, REQ-001.21);
- располагаться с учётом панели задач основного монитора (рабочая область из `GetMonitorInfo.rcWork`).

### 4. Буфер обмена

- `Toolkit.getDefaultToolkit().systemClipboard.setContents(transferable, owner)` с `DataFlavor.imageFlavor`. AWT на Windows публикует изображение как `CF_DIB` (прозрачность теряется).
- Если буфер занят другим процессом, AWT бросает `IllegalStateException` — нужен цикл повторов (REQ-001.25).
- Доступность данных после выхода из приложения (REQ-001.26) **требует проверки** прототипом. При необходимости — прямая запись `CF_DIB` / `CF_DIBV5` и формата `PNG` через WinAPI (`OpenClipboard` / `SetClipboardData`).
- Некоторые приложения при вставке предпочитают зарегистрированный формат `PNG`. Добавление этого формата повысит совместимость (AC-1 в US-004).
- Облачная история буфера (Win+V): существуют документированные форматы `ExcludeClipboardContentFromMonitorProcessing` / `CanIncludeInClipboardHistory` / `CanUploadToCloudClipboard`. По решению пользователя снимки **не исключаются** (REQ-001.58), эти форматы в v1 не используются.

### 5. Кодирование и запись PNG

- `ImageIO.write(image, "png", file)` — стандартный путь. Время кодирования 4K на одном ядре может быть порядка 0,5–1,5 с. Близко к границе REQ-001.N4 — **нужен замер**. Варианты ускорения: понижение уровня сжатия (`ImageWriteParam`), сторонний PNG-кодер.
- Захват из GDI в формате BGRA → `BufferedImage.TYPE_INT_RGB` без альфа-канала: файл меньше, кодирование быстрее.
- Атомарность (REQ-001.32): запись во временный файл в той же директории + `Files.move(..., ATOMIC_MOVE)`.
- Память: 3 × 4K в `TYPE_INT_RGB` ≈ 99,5 МБ на кадр. Для «Области» одновременно хранятся замороженный кадр и вырезка, плюс копия для буфера обмена. Укладывается в REQ-001.N6 при `-Xmx` ≥ 512 МБ; нужно избегать лишних копий.

### 6. Директория по умолчанию и хранение настроек

- `FOLDERID_Screenshots` и `FOLDERID_Pictures` получаются через `SHGetKnownFolderPath` (в JNA есть `Shell32Util.getKnownFolderPath`). Так учитывается перенаправление в OneDrive. Конструкция `System.getProperty("user.home") + "\\Pictures"` при перенаправлении даёт неверный путь.
- Пути с кириллицей: Java NIO на Windows работает через UTF-16 API, проблем не ожидается. Нужно не использовать сторонние нативные вызовы с ANSI-версиями функций (`...A`).
- Хранение настроек:
  - `java.util.prefs` на Windows пишет в реестр `HKCU\Software\JavaSoft\Prefs` и экранирует не-ASCII символы — работает, но значения неудобно читать и переносить;
  - файл (JSON/properties) в `%APPDATA%\fast-cow-screenshot\` прозрачен, переносим и легко сбрасывается.

  **Рекомендуется** файл — оформить ADR.

## Риски

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| Неверная склейка или масштабирование при смешанном DPI (нарушение REQ-001.20) | Высокая | Высокое | GDI + `EnumDisplayMonitors` в режиме `PER_MONITOR_AWARE_V2`; автотест с эталонным узором на конфигурации 100 % + 150 % |
| Режим DPI awareness процесса JVM конфликтует с нативными вызовами (JDK выставляет свой режим) | Средняя | Высокое | В прототипе проверить `GetAwarenessFromDpiAwarenessContext`; при необходимости `SetThreadDpiAwarenessContext` на время захвата |
| Отрисовка оверлея не 1:1 при масштабе ≠ 100 % (размытие, сдвиг выделения) | Средняя | Высокое | Окно на каждый монитор; учитывать scale-фактор при отрисовке; включить в прототип |
| Горячая клавиша занята системой или другими приложениями | Средняя | Среднее | Комбинации с модификаторами по умолчанию (`Ctrl+Shift+1/2/3`); уведомление о конфликте; переназначение (REQ-001.4) |
| `Ctrl+Shift+1/2/3` перестают работать в других приложениях (например, форматы в Excel) | Высокая | Низкое | Переназначение (REQ-001.4); упоминание в документации пользователя |
| Системные уведомления Windows не позволяют задать длительность 3 с | Высокая | Среднее | Собственное окно уведомления (раздел 3a) |
| Некорректная отрисовка указателя (анимированные, монохромные, увеличенные курсоры) | Средняя | Низкое | `GetCursorInfo` + `DrawIconEx`; проверка в прототипе |
| Кодирование PNG 4K не укладывается в REQ-001.N4 | Средняя | Среднее | Фоновая запись; настройка уровня сжатия; замер в прототипе |
| Данные буфера теряются после выхода из приложения | Низкая | Среднее | Проверить в прототипе; при необходимости прямой WinAPI |
| Чёрный кадр для DRM, exclusive fullscreen, защищённого рабочего стола | Высокая | Низкое | Задокументировать как ограничение (REQ-001 §5) |
| Искажение цветов при включённом HDR | Средняя | Низкое | Известное ограничение v1; в будущем — Windows.Graphics.Capture |
| Антивирусы реагируют на нативный захват экрана или хуки | Низкая | Среднее | `RegisterHotKey` вместо низкоуровневого хука; подпись исполняемого файла |
| Пиковое потребление памяти на больших виртуальных столах | Средняя | Среднее | `TYPE_INT_RGB`, минимизация копий, лимит heap, тест на 3 × 4K |

## Выводы и рекомендации

- Для v1 (только Windows) рекомендуется нативный слой через **JNA**:
  - `EnumDisplayMonitors` / `GetMonitorInfo` / `MonitorFromPoint` — топология мониторов;
  - GDI `BitBlt` — захват пикселей; `GetCursorInfo` + `DrawIconEx` — опциональная отрисовка указателя;
  - `RegisterHotKey` — глобальные клавиши;
  - `SHGetKnownFolderPath` — директория по умолчанию.

  AWT `Robot` оставить запасным вариантом.
- Режим «Область» реализовать по схеме «замороженного кадра» с отдельным окном оверлея на каждый монитор.
- Уведомления делать собственным окном приложения, а не системным toast: только так выполняется требование «3 секунды» (REQ-001.54).
- До реализации провести **spike** (оценка 2–3 дня). Проверить:
  - захват на конфигурации 100 % + 150 %;
  - захват 3 × 4K;
  - отрисовку оверлея 1:1;
  - кодирование PNG 4K;
  - буфер обмена после выхода из приложения;
  - отрисовку указателя;
  - работу на Windows 10 22H2 и Windows 11.

  По результатам подтвердить NFR REQ-001.N1–N6.
- Оформить ADR:
  1. Механизм захвата экрана на Windows (GDI через JNA vs AWT Robot).
  2. Механизм глобальных горячих клавиш (`RegisterHotKey` через JNA).
  3. UI-фреймворк (Compose Multiplatform Desktop vs Swing vs JavaFX) с учётом трея, оверлея 1:1 и собственного окна уведомлений.
  4. Формат и место хранения настроек (файл в `%APPDATA%` vs `java.util.prefs`): директория по умолчанию, последняя папка «Сохранить как», горячие клавиши, флажок указателя.
