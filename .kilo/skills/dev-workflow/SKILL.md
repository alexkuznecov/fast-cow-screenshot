# Процесс разработки по задачам

## Статусы задачи (TASK)

| Статус | Кто ставит | Когда |
|---|---|---|
| `Ready` | Tech | Задача готова к работе |
| `In Progress` | Dev | Начата реализация или возобновлена после закрытия CLR |
| `Blocked` | Dev | Есть открытый блокирующий CLR |
| `Review` | Dev | Всё реализовано, сборка и тесты зелёные, журнал заполнен |
| `Done` | Пользователь (или Dev по явному указанию) | Результат принят |

Статус меняется в **двух** местах: в шапке файла задачи и в таблице «Задачи» `docs/tech/README.md`.

## Запрос уточнения (CLR)

- Шаблон: `templates/clarification.md` (рядом с этим файлом).
- Папка: `docs/tech/clarifications/`, имя: `CLR-NNN-<slug>.md`, где `NNN` — следующий свободный трёхзначный номер (glob `CLR-*.md`), `<slug>` — kebab-case на латинице.
- Адресат: `Tech` (как реализовать), `Analyst` (что должна делать система), `User` (окружение, ручная проверка, выбор без архитектурных последствий).
- Статусы CLR: `Open` → `Answered` (адресат записал ответ) → `Closed` (Dev применил ответ); также `Withdrawn` (вопрос снят).
- После создания добавь строку в таблицу «Запросы уточнения» `docs/tech/README.md`.

### Правила хорошего CLR

1. Один CLR — один вопрос (или тесно связанная группа вопросов по одному месту задачи).
2. Цитируй документ дословно: файл, раздел, текст.
3. Покажи, что уже проверено: какие файлы прочитаны, какие команды запущены, вывод ошибки (сокращённо, но с ключевыми строками).
4. Предложи 2–3 варианта решения с последствиями; рекомендуемый — первым. Решение принимает адресат, а не Dev.
5. Сформулируй вопрос так, чтобы на него можно было ответить выбором варианта или одной фразой.
